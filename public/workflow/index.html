01 / INTAKE

거래처 접수 웹앱

외부 거래처가 입력한 정보는 Vercel 웹앱을 거쳐 Notion 거래처DB에 저장됩니다. 업무용으로 쓰지 않는 속성은 웹앱 저장 대상에서 제외하는 방향으로 정리했습니다.

기존 방식

담당자가 여러 문서에 재입력

원장님 전달 내용과 내부 DB 값이 달라지고, 사용하지 않는 속성까지 함께 저장됐습니다.

발생 문제

누락·중복·담당자 공백

같은 병원이 중복 생성되거나 담당마케터 없이 후속 자동화가 멈출 수 있었습니다.

개선 중인 방향

웹앱에서 허용 필드만 저장

거래처명으로 중복을 검사하고, 실제 운영에 쓰는 값만 거래처DB에 반영합니다.

01B / AS-IS SYSTEM

회의 전 필수
현재 내부 시스템 Flow

신실장님 지시사항: 회의 전에 현재 내부 시스템 흐름을 먼저 확인합니다. 지금은 하나의 마스터가 아니라 마케팅 계정정보, 블로그 구버전, 블로그 신버전이 서로 다른 기준으로 운영되고 있어 거래처명·계정·담당자·발행 현황을 대조해야 합니다.

기존 방식

세 시트가 각자 다른 이름 사용

마케팅 계정, 구버전 계약, 신버전 발행 데이터가 별도 기준으로 관리됩니다.

발생 문제

같은 병원이 다른 거래처처럼 보임

계정·담당자·계약 건수·병원코드가 정확히 연결되지 않습니다.

개선 중인 방향

거래처DB ID 중심 매핑

기존 값은 유지한 채 공식 거래처 하나에 세 원천의 식별자를 연결합니다.

POC 설계 완료
운영 기준

회의 전에 불일치부터 확인

매핑되지 않은 계정과 병원코드를 회의 안건으로 먼저 올리고 임의로 합치지 않습니다.

원본 삭제 금지
AS-IS 1

마케팅 계정정보

병원명 → 항목 → 아이디·URL 구조입니다. 플랫폼별 계정은 모여 있지만 병원명 표기와 계정 행이 분리돼 있습니다.

AS-IS 2

블로그 구버전

병원 → 계약 건수 → 콘텐츠 유형 → 담당자 중심입니다. 병원별 개별 탭과 전체 탭이 함께 존재합니다.

AS-IS 3

블로그 신버전

병원코드 → 채널 → 콘텐츠 → 발행 일정·성과 중심입니다. 운영 단위는 정교하지만 기존 시트와 식별자가 다릅니다.

PRE-MEETING

불일치 대조

병원명 정규화, 블로그 ID, 계약 건수, 담당자, 구·신버전 이관 여부를 확인한 뒤 회의 안건을 확정합니다.

SOURCE 01

기존 마케팅 계정정보

공식 병원명 · 플랫폼 · 계정 식별자 · URL이 핵심입니다. 계정값과 실사용자 정보는 공개 문서에 싣지 않습니다.

SOURCE 02

블로그 시트 구버전

계약 건수 · 콘텐츠 유형 · 내부/외주 · 담당자 구조입니다. 병원명과 담당자 실명은 거래처DB ID로 치환합니다.

SOURCE 03

블로그 시트 신버전

병원코드 · 스케줄ID · 채널 · 발행일 · 성과를 추적합니다. 공개 화면에는 실제 코드와 계정값을 표시하지 않습니다.

POC 결론: 세 시트를 바로 합치거나 삭제하지 않습니다. 먼저 거래처DB의 공식 거래처 ID를 공통 키로 두고 공식 거래처명 ↔ 기존 계정 ↔ 구버전 행 ↔ 신버전 병원코드 매핑표를 만든 뒤, 불일치가 0건인 범위부터 단계적으로 이관합니다.
02 / OPENING

신규개원 12개 업무

`신규 업무 생성`이 체크되고 생성 상태가 미완료인 거래처만 처리합니다. 기존 표준 업무는 유지하고 빠진 업무만 보완합니다.

기존 방식

거래처당 ‘신규 개원 세팅’ 1건

업무 범위가 한 페이지에 뭉쳐 담당자와 완료 기준이 흐렸습니다.

발생 문제

누락과 중복을 판별하기 어려움

일부 작업만 끝나도 전체가 끝난 것처럼 보이고 재실행 시 중복될 수 있었습니다.

개선 중인 방향

표준 12개 업무로 분해

업무명 단위로 존재 여부를 검사하고 빠진 업무만 체크리스트와 함께 생성합니다.

12개 표준 확정
운영 기준

동일명 2건이면 즉시 중단

중복이 의심되면 자동 수정하지 않고 거래처와 업무명을 보고합니다.

멱등성 적용
1

대상 확인

체크 여부와 업무 생성 상태를 검사합니다.

2

중복 검사

동일 거래처·표준 업무명 기준으로 0·1·2건 이상을 판정합니다.

3

누락 업무 생성

첫 인사부터 최종 개원 점검까지 표준 12종을 구성합니다.

4

체크리스트 연결

업무마다 필터된 업무 체크리스트DB 보기를 연결합니다.

5

거래처 완료 처리

모든 검증 성공 후에만 Relation과 생성완료 상태를 저장합니다.

03 / MEETING → DONE

미팅 기록부터
업무분배·완료까지

녹음과 수기 모두 같은 검토 관문을 통과합니다. 사람이 실행할 내용을 확정하고 승인한 뒤에만 업무가 생성되며, 체크리스트가 100%가 되어야 종료됩니다.

기존 방식

녹음 요약·수기 메모를 그대로 보관

결정, 요청, 아이디어와 실제 실행 업무가 한 본문에 섞였습니다.

발생 문제

모호한 문장까지 업무화될 위험

담당팀과 완료 기준이 없는 업무가 생성되거나 같은 요청이 반복될 수 있습니다.

개선된 방식

전처리 후 사람 승인

녹음과 수기 모두 액션 후보로 정리하고 담당자가 확정한 문장만 생성 요청합니다.

E2E 생성 QA 완료
운영 기준

완료 상태 + 생성 요청 체크

거래처 1곳, 실행 문장, 담당자까지 유효할 때만 (신)업무DB에 저장합니다.

무승인 생성 금지

🎙 녹음으로 시작

  1. Notion 음성 메모 또는 녹음 파일 저장
  2. 받아쓰기·요약으로 논의 내용을 구조화
  3. 결정사항과 사내 실행 항목 후보를 추출
  4. 담당자가 원문과 비교해 액션 아이템을 확정

✍️ 수기로 시작

  1. 미팅 본문은 형식 없이 자유롭게 작성 가능
  2. 담당자가 결정·요청·검토·아이디어를 구분
  3. 실행이 확정된 항목만 액션 아이템으로 이동
  4. 업무 하나당 한 줄로 정리하고 모호한 표현 제거
공통 승인점
사람이 내용을 검토한 뒤 미팅 상태=완료 + 업무 생성 요청=체크
STEP 1

미팅 기록 수집

녹음 또는 수기 본문과 거래처·참석자·미팅 담당자를 한 미팅 페이지에 모읍니다.

STEP 2

내용 전처리

인사말·반복·아이디어를 걷어내고 실제 실행이 필요한 문장만 업무 후보로 정리합니다.

STEP 3

사람 검토·승인

업무명·대상 거래처·실행 범위를 확인합니다. 자동 요약만으로는 생성되지 않습니다.

STEP 4

안전 조건 검사

완료 상태, 생성 요청, 거래처 1곳, 유효 액션을 확인하고 중복 업무를 검사합니다.

STEP 5

팀 분류

내용을 마케팅·바이럴·디자인·웹 업무로 분류합니다. 미지원·모호 항목은 생성하지 않습니다.

STEP 6

담당자 결정

마케팅은 거래처DB 담당마케터를 우선합니다. 사람DB Relation이 통합 권한 때문에 가려진 경우에만 미팅 담당자 1명을 안전 대체값으로 사용하며, 다른 팀 업무도 미팅 담당자 1명을 요구합니다.

STEP 7

(신)업무DB 생성

업무명·관련거래처·담당팀·담당자·상태를 저장하고 원본 미팅 Relation을 연결합니다.

STEP 8

직원 실행

업무 페이지의 필터된 체크리스트에서 실행하고 결과 링크·캡처·접수번호 등 증빙을 남깁니다.

STEP 9

진행률 자동 집계

업무 체크리스트DB의 완료 체크 수가 Rollup으로 집계되어 진행률이 올라갑니다.

STEP 10

업무 완료·종료

체크리스트가 1개 이상이고 모두 완료되면 업무상태를 완료로 바꾸고 종료일을 기록합니다.

오류 시 동작: 거래처 없음·복수 연결, 담당자 불명확, 동일 업무 중복, 지원하지 않는 팀이면 업무를 만들지 않습니다. 원인을 업무 생성 오류에 기록하고 운영자가 수정한 뒤 다시 승인합니다.

반려·중단 조건: 환자·증례 구분 불가, 비정상적인 대량 파일, 계약 종료 거래처, 계약과 배정 건수 불일치, 담당 작가 미확정, 중복·누락·작가명 오기가 있으면 발행이나 정산으로 넘기지 않습니다. 내부 담당자가 원인을 해결한 뒤 다시 배정합니다.
